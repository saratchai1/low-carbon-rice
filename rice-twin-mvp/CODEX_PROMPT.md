# Master prompt for Codex

You are a senior full-stack geospatial engineer and agricultural digital-MRV architect. Build or extend a working MVP named **Rice Twin**, an operational Digital Twin platform for low-carbon rice production and Alternate Wetting and Drying (AWD).

Work autonomously. Inspect the existing repository first, preserve working behavior, and improve it incrementally. Do not replace working modules without a concrete reason. Do not stop at wireframes or pseudocode: produce runnable code, database migrations or initialization, tests, seed data, Docker configuration, and clear documentation.

## 1. Product objective

Create a browser-based platform that represents each rice plot as a live Digital Twin. It must combine plot identity, geometry, crop-season state, water-level observations, AWD cycles, field activities, evidence, remote-sensing imagery, data-quality flags, recommendations, and a carbon-MRV-ready audit trail.

The MVP must support this closed loop:

```text
Observe field data
→ update the plot state
→ evaluate AWD/data-quality rules
→ show a recommendation or alert
→ record an action
→ observe the result
→ preserve evidence for MRV
```

The system is not a 3D visualization. Prioritize operational state, traceability, and geospatial evidence.

## 3. Preferred architecture

Use a simple, maintainable stack:

- Backend: Python, FastAPI, Pydantic, SQLAlchemy
- Database: PostgreSQL with PostGIS
- Frontend: TypeScript/React or the existing lightweight frontend; MapLibre GL JS for the map
- Raster processing: Rasterio/GDAL
- Object/file storage for MVP: mounted local volume with a clean storage abstraction
- Production-ready raster path: Cloud-Optimized GeoTIFF (COG) plus TiTiler; implement as an optional next-stage adapter if not required for the first runnable slice
- Containerization: Docker Compose
- API specification: OpenAPI generated by FastAPI
- Tests: pytest for backend; appropriate frontend tests if a frontend build system exists

Use current stable, mutually compatible package versions and pin them in a lockfile or constrained requirements. Do not require proprietary map tokens. A public raster basemap is acceptable for local demonstration, with attribution.

## 4. Functional modules

### 4.1 Plot registry and map

Implement:

- plot list and plot detail
- GeoJSON FeatureCollection API
- PostGIS geometry storage with SRID 4326
- spatial index
- geometry validity checks
- center, area, and boundary-source metadata
- map fit-to-plot
- clear synthetic-boundary warning
- future-ready support for multiple plots and crop seasons

### 4.2 Plot Digital Twin state

For each plot and crop season, represent at least:

```text

last_observation_at
recommendation

```

Do not store only the latest value. Preserve source observations and derive the current state from observations where practical.

### 4.3 Field activity and evidence timeline

Support activities such as:

Each activity needs:

```text

latitude/longitude when available
quantity and unit when relevant

```

Provide create/list APIs and a timeline UI. Adding a water-level observation must update or trigger recomputation of the current Twin state.

### 4.4 AWD rule engine

Implement a configurable rules layer, not hard-coded UI logic. Begin with demonstrative rules and label them as demo rules until an agronomist approves thresholds.

Examples:

```text
IF water level is below a configured threshold
AND the crop stage is not marked sensitive
AND no material rain is expected within a configured horizon
THEN recommend irrigation.
```

```text
IF a manual record says the plot is dry
BUT sensor or imagery evidence indicates persistent inundation
THEN create a data-conflict alert.
```

Rules must output:

```text
rule_id
rule_version
severity
explanation
inputs used
evaluated_at
recommended action
```

Do not present demo thresholds as universal agronomic advice.

### 4.5 Satellite/raster imagery ingestion

The owner will provide downloaded satellite imagery later. Implement a safe upload flow now.

MVP accepted input:

- `.tif` or `.tiff`
- georeferenced GeoTIFF or COG
- CRS and affine geotransform embedded in the file

Upload form fields:

```text
plot_id
captured_at optional
red_band
green_band
blue_band
file
```

Processing requirements:

1. Stream the upload; do not load the entire file into RAM.
2. Enforce configurable file-size and extension limits.
3. Sanitize filenames and prevent path traversal.
4. Open with Rasterio and reject files with no CRS.
5. Extract CRS, transform, bounds, dimensions, band count, dtype, nodata, and basic tags.
6. Transform bounds to EPSG:4326.
7. Create a browser preview with alpha transparency and a robust percentile stretch.
8. Preserve the original file unchanged.
9. Record a content hash for evidence integrity.
10. Show the preview as an image/raster layer in MapLibre with opacity control and visibility toggle.
11. Keep a catalog with capture date, upload date, CRS, dimensions, selected bands, footprint, source, and processing status.
12. Reject invalid requested band numbers with an explicit error.

For large production scenes, add a documented upgrade path:

```text
upload → validate → convert/validate as COG → object storage → STAC item → TiTiler tiles → MapLibre raster source
```

Do not fabricate remote-sensing classifications. A satellite image is supporting evidence, not automatic proof that AWD requirements were met.

For PNG/JPEG, do not guess geolocation. Require a world file, bounding box, four corner coordinates, or a GeoJSON footprint before overlaying it.

### 4.6 Data quality

Implement transparent data-quality checks, for example:

- missing observations during a critical period
- impossible chronology
- invalid or overlapping plot geometry
- water-level jump beyond a configurable rate
- prolonged unchanged sensor values
- activity/observation conflict
- imagery footprint not intersecting the plot
- missing evidence for a claimed action

Expose the individual checks behind the confidence score. Never show a score without explaining its components.

### 4.7 Carbon MRV readiness

Add a methodology-versioned data model, but do not invent a certified formula. The module must distinguish:

```text
baseline scenario
project activity
emission sources
activity data
emission factors
calculation version
uncertainty
exclusions
verification status
creditable amount
issued amount
retired amount
```

Until an approved methodology and factors are configured, display:

```text
GHG calculation not configured — no carbon-credit claim can be made.
```

Every future calculation must be reproducible from input data, factor version, formula version, and approval records. No sensor reading directly equals a carbon credit.

### 4.8 Audit trail and security

Implement or scaffold:

- authentication-ready user model
- role-based access boundaries for farmer, field officer, project manager, carbon specialist, verifier, and admin
- append-only audit log for create/update/verify operations
- old value, new value, actor, timestamp, reason, request ID
- read-only verifier view
- no silent deletion of evidence

The local MVP may run without login, but the code and schema must not make later RBAC impossible.

## 5. Required UI

Use Thai labels for the main UI and English identifiers in code. Include:

1. **Operations map** — plot geometry, current state, imagery layers, map legend, synthetic-boundary warning.
2. **Plot Digital Twin panel** — current water level, AWD cycle, dry days, crop stage, recommendation, risk, confidence, timestamp.
3. **Water history chart** — observations over time with a visible zero-ground line.
4. **Activity form and evidence timeline**.
5. **Imagery upload and catalog** — selected filename, capture date, band inputs, processing feedback, visibility and opacity controls.
6. **Data quality panel** — component checks, conflicts, missing data.
7. **Carbon MRV panel** — methodology status and explicit “not configured” state until valid configuration exists.

Responsive behavior must support desktop and tablet widths. Accessibility requirements: keyboard-focus states, form labels, adequate contrast, and map-independent access to key plot data.

## 10. Acceptance criteria

The work is complete only when:

1. `docker compose up --build` starts the database and app.
2. The browser opens a map centered near `[100.274733, 14.469728]`.
3. The synthetic plot is visible and clearly marked non-cadastral.
4. Current AWD/Twin state and activity timeline load from the API, not hard-coded DOM text.
5. A water-level record can be submitted and appears in the history/chart.
6. A georeferenced test GeoTIFF can be uploaded and overlaid in the correct location.
7. Imagery opacity and visibility controls work.
8. Invalid raster inputs return useful errors without leaving orphan files.
9. Database state persists across container restarts.
10. API documentation is available.
11. README contains run, reset, upload, band-selection, limitation, and production-upgrade instructions.
12. Tests pass with a documented command.

## 11. Engineering constraints

- Keep secrets out of the repository.
- Use environment variables and an `.env.example`.
- Use UTC internally; display Asia/Bangkok time in the UI.
- Use migrations for schema evolution when moving beyond the seed prototype.
- Add database indexes for plot ID, event time, imagery capture time, and spatial geometry.
- Avoid N+1 query patterns.
- Handle upload/process errors transactionally and remove partial files.
- Log processing status without logging sensitive user data.
- Preserve source files and evidence hashes.
- Do not claim certification, verified emissions reduction, or carbon credits.
